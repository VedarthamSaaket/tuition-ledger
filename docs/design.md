# Design and provenance

All records are synthetic and produced by the generator; no external dataset or real student information is used. The manifest in each dataset records the seed, generator command, counts and checksums. Programs, terms, students and fee schedules are created before enrollments and invoices, followed by eligibility, awards, payments, allocations and refunds. Event and decision records explain transitions and rule outcomes. The generated data dictionary describes keys, fields and relationships.

The generator uses a fixed snapshot date and integer paise; exported money values are Indian rupees (INR). Existing synthetic amounts are retained numerically, not converted at an exchange rate. It creates a valid baseline, then adds deliberately labelled violations to exercise the detector. Ground truth is exported separately and is not read by the detector; validation may use labels to distinguish expected injected failures from unexplained failures. Evaluation compares detected entity/type pairs with those labels. Precision and recall here measure detection of these specific constructed violations, not performance on independent real-world data.

For seed 20261022 the full profile produces 10,000 students, 20 programs, 30,000 invoices, 15,000 awards and 50,000 payments. A local full-profile validation returned 96 passing and 7 expected checks; detection found all 310 injected labels with no false positives. Two separate CSV generations with different Python hash seeds produced identical checksums, recorded in `full_reproducibility.json`. The enrollment count is 29,940 because deliberately duplicated invoices share enrollments.

Fee schedules are selected by program, term and effective date. Award criteria and caps are in `ledger/domain/catalog.py` and `ledger/domain/rules.py`. Payment allocations follow fee priority. The ledger records signed charges, credits, payments and refunds; snapshots are derived from those records. Withdrawal reversals apply to eligible net charge lines, based on the schedule in the rules. The live API locks relevant rows and appends audit records in the same transaction as financial changes.

Trade-offs: the application uses local PostgreSQL and header-selected demo roles rather than a production identity system; it has no real payment integration. The seeded dataset includes intentional exceptions and should not be treated as a clean production ledger. Refund processing is deliberately bounded by available credit and payment history. Live actions and concurrent use need additional independent review, stronger database invariants, migrations, authentication and adversarial testing before any real deployment.
